===============================================================================
Sample rendered configuration - SPINE1
===============================================================================
This is a plain-text example of the "nv set" command sequence Ansible
generates and stages onto cl-sp-1 from the cumulus_underlay role's
nv_underlay.sh.j2 template. It is for reference/reading only and is not
consumed by any playbook - the actual commit happens via "nv config apply"
after this script runs (see roles/cumulus_underlay/tasks/main.yml).

Role in fabric : spine (device_role: spine)
Management IP  : 192.168.122.32
Loopback IP    : 10.0.0.1/32
Router ASN     : 65001
Fabric MTU     : 9216
Uplinks        : one unnumbered swp per leaf (6 leafs -> swp1-swp6)

-------------------------------------------------------------------------------
nv set commands (loopback + fabric-facing ports + underlay/EVPN-transit BGP)
-------------------------------------------------------------------------------
nv set interface lo ip address 10.0.0.1/32

nv set interface swp1 link state up
nv set interface swp1 link mtu 9216
nv set vrf default router bgp neighbor swp1 type unnumbered
nv set vrf default router bgp neighbor swp1 peer-group UNDERLAY

nv set interface swp2 link state up
nv set interface swp2 link mtu 9216
nv set vrf default router bgp neighbor swp2 type unnumbered
nv set vrf default router bgp neighbor swp2 peer-group UNDERLAY

nv set interface swp3 link state up
nv set interface swp3 link mtu 9216
nv set vrf default router bgp neighbor swp3 type unnumbered
nv set vrf default router bgp neighbor swp3 peer-group UNDERLAY

nv set interface swp4 link state up
nv set interface swp4 link mtu 9216
nv set vrf default router bgp neighbor swp4 type unnumbered
nv set vrf default router bgp neighbor swp4 peer-group UNDERLAY

nv set interface swp5 link state up
nv set interface swp5 link mtu 9216
nv set vrf default router bgp neighbor swp5 type unnumbered
nv set vrf default router bgp neighbor swp5 peer-group UNDERLAY

nv set interface swp6 link state up
nv set interface swp6 link mtu 9216
nv set vrf default router bgp neighbor swp6 type unnumbered
nv set vrf default router bgp neighbor swp6 peer-group UNDERLAY

nv set vrf default router bgp router-id 10.0.0.1
nv set vrf default router bgp autonomous-system 65001

nv set vrf default router bgp peer-group UNDERLAY remote-as external
nv set vrf default router bgp peer-group UNDERLAY bfd enable on
nv set vrf default router bgp peer-group UNDERLAY address-family ipv4-unicast enable on
nv set vrf default router bgp peer-group UNDERLAY address-family l2vpn-evpn enable on

nv set vrf default router bgp address-family ipv4-unicast network 10.0.0.1/32
nv set vrf default router bgp address-family ipv4-unicast multipaths ebgp 2
nv set vrf default router bgp address-family l2vpn-evpn enable on

nv set vrf default router bgp enable on

nv config apply -y

-------------------------------------------------------------------------------
Notes
-------------------------------------------------------------------------------
- Spines only carry the underlay (IPv4 unicast + EVPN transit); they hold no
  VNIs and no tenant VRFs, so there is no VXLAN/overlay role applied here
  (site.yml only applies cumulus_underlay to the "fabric" group, which spines
  are in, but cumulus_overlay is leaf-only).
- There's no explicit "attribute-unchanged next-hop" command here (unlike the
  old raw-FRR frr.conf this used to render) - NVUE's default next-hop-setting
  ("auto") is FRR's native behaviour for the l2vpn-evpn address family, which
  already passes EVPN routes through the spine with the originating leaf's
  VTEP IP intact.
- No daemon-enable or frr-restart step either - "nv config apply" regenerates
  frr.conf/daemons and restarts whatever's needed atomically as part of the
  commit.
