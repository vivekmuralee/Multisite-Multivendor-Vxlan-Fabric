===============================================================================
Hand-apply configuration guide - SPINE2 (cl-sp-2)
===============================================================================
Step-by-step NVUE configuration for cl-sp-2, applied by hand one layer at a
time. Each step stages "nv set" commands, applies them, then verifies the
result before moving on.

Every line starting with "#" is a shell comment, so a whole step block can be
pasted into the switch CLI as-is. The same commands are generated by the
Ansible template roles/cumulus_underlay/templates/nv_underlay.sh.j2.

Role in fabric : spine
Management IP  : 192.168.122.33
Loopback IP    : 10.0.0.2/32
Router ASN     : 65002
Fabric MTU     : 9216 (9215 on swp links)
Downlinks      : swp1 -> cl-lf-1 ... swp6 -> cl-lf-6

-------------------------------------------------------------------------------
Before you start
-------------------------------------------------------------------------------
# Is anything already staged but not applied? (should print nothing)
nv config diff

# Throw away a half-staged change if you need to start a step again
#   nv config detach

# Leftover pre-NVUE config: the old Ansible roles wrote ifupdown2 fragments
# (00-loopback / 10-uplinks / 20-vxlan / 30-external .intf) here. NVUE's
# /etc/network/interfaces still sources this directory, so they get merged
# with NVUE's config and break ifreload, e.g.
#   "vni10010: mixing traditional vxlan with single vxlan device is not supported"
#   "RTNETLINK answers: Address already in use"
# Move them out before step 1 (should list nothing afterwards):
ls -l /etc/network/interfaces.d/
sudo mkdir -p /root/pre-nvue-backup
sudo mv /etc/network/interfaces.d/*.intf /root/pre-nvue-backup/ 2>/dev/null
ls /etc/network/interfaces.d/
# Old per-VNI devices still in the kernel (leafs only; none = no output)
ip -br link | grep -E "^vni[0-9]+"
#   remove any listed with:  sudo ip link del <name>

-------------------------------------------------------------------------------
Step 1 - Loopback and leaf-facing ports
-------------------------------------------------------------------------------
# Loopback = router-id and the address leafs ping to test the underlay.
nv set interface lo ip address 10.0.0.2/32

# One port per leaf. No IP addresses: BGP unnumbered (step 2) peers over the
# automatic IPv6 link-local address. MTU 9215 carries VXLAN-encapsulated
# jumbo frames.
nv set interface swp1 link state up
nv set interface swp1 link mtu 9215
nv set interface swp2 link state up
nv set interface swp2 link mtu 9215
nv set interface swp3 link state up
nv set interface swp3 link mtu 9215
nv set interface swp4 link state up
nv set interface swp4 link mtu 9215
nv set interface swp5 link state up
nv set interface swp5 link mtu 9215
nv set interface swp6 link state up
nv set interface swp6 link mtu 9215

nv config apply -y

# Verify
nv show interface lo ip address           # 10.0.0.2/32
nv show interface --view=brief            # swp1-swp6 up, MTU 9215
nv show service lldp neighbor             # swpN -> cl-lf-N

-------------------------------------------------------------------------------
Step 2 - Underlay BGP (eBGP unnumbered) + EVPN transit
-------------------------------------------------------------------------------
# Global BGP identity, inherited by every BGP instance on the switch.
nv set router bgp autonomous-system 65002
nv set router bgp router-id 10.0.0.2
nv set router bgp enable on

# Peer-group shared by all six leaf sessions. Same session carries IPv4
# (loopbacks) and l2vpn-evpn (overlay routes the spine relays between leafs).
nv set vrf default router bgp peer-group UNDERLAY remote-as external
nv set vrf default router bgp peer-group UNDERLAY bfd enable on
nv set vrf default router bgp peer-group UNDERLAY address-family ipv4-unicast enable on
nv set vrf default router bgp peer-group UNDERLAY address-family l2vpn-evpn enable on

# Neighbors are interfaces, not IPs (unnumbered).
nv set vrf default router bgp neighbor swp1 type unnumbered
nv set vrf default router bgp neighbor swp1 peer-group UNDERLAY
nv set vrf default router bgp neighbor swp2 type unnumbered
nv set vrf default router bgp neighbor swp2 peer-group UNDERLAY
nv set vrf default router bgp neighbor swp3 type unnumbered
nv set vrf default router bgp neighbor swp3 peer-group UNDERLAY
nv set vrf default router bgp neighbor swp4 type unnumbered
nv set vrf default router bgp neighbor swp4 peer-group UNDERLAY
nv set vrf default router bgp neighbor swp5 type unnumbered
nv set vrf default router bgp neighbor swp5 peer-group UNDERLAY
nv set vrf default router bgp neighbor swp6 type unnumbered
nv set vrf default router bgp neighbor swp6 peer-group UNDERLAY

nv set vrf default router bgp address-family ipv4-unicast network 10.0.0.2/32
nv set vrf default router bgp address-family ipv4-unicast multipaths ebgp 2
nv set vrf default router bgp address-family l2vpn-evpn enable on

nv set vrf default router bgp enable on

nv config apply -y

# Verify
nv show vrf default router bgp neighbor           # swp1-swp6 established
sudo vtysh -c "show bgp summary"
sudo vtysh -c "show bgp l2vpn evpn summary"       # EVPN AF up to every leaf
sudo vtysh -c "show bgp ipv4 unicast"             # leaf loopbacks 10.0.0.11-16
ping -c3 -I lo 10.0.0.11                          # leaf loopback reachable

-------------------------------------------------------------------------------
Step 3 - Save
-------------------------------------------------------------------------------
nv config save
nv config show -o commands                        # full config in set syntax

-------------------------------------------------------------------------------
Notes
-------------------------------------------------------------------------------
- Spines carry no VNIs and no tenant VRF: no nve vxlan, no bridge VLANs, no
  SVIs. They only relay EVPN routes between leafs.
- No "attribute-unchanged next-hop" command: for the l2vpn-evpn address
  family FRR already keeps the originating leaf's VTEP IP as next-hop, so
  tunnels go leaf-to-leaf directly.
- "nv config apply" regenerates frr.conf and restarts FRR as needed; there is
  no separate daemon-enable or restart step.
- See RUNBOOK.md section 9 for spine-specific checks.
